ARIA

One operations chat for two companies: reports, finance, marketing and code audits, each kept in its own lane.

2companies, fully separated
~$0.08per work report (was $0.30)
214isolation checks on every deploy
100%of writes wait for a human
01

Why it exists

The team was opening ten dashboards to answer one question, and writing weekly reports by hand. ARIA answers in one chat with the live numbers, drafts the report, plans content and audits code. Two companies share the platform, so the hardest rule is that each one only ever sees its own data.

Used byStaff of CAP and MatchupSkills, from marketing to finance, each with their own role.
02

One request, step by step

Click a step, or press play, to follow one real request through the system.

Step 1 / 7 · Team member

A request

“Write this week’s marketing report and suggest three posts for next week.”

trace
"Write this week's marketing report and suggest three posts for next week."

Step 2 / 7 · Session

Role check

The admin session says who is asking and which role they have. A marketing role can read marketing and content; finance tools are not even offered to the model.

trace
const me = await requireStaff(req);                 // role: marketingconst tools = TOOLS.filter((x) => x.roles.includes(me.role));// finance_summary, payroll, users → not in the list at all

Step 3 / 7 · Tenant

Lock the company

The company is taken from the login, never from the chat. Every query in this request is pinned to that company’s data. A prompt that says “show me the other company” changes nothing.

trace
const tenant = tenantFor(me);                        // from the sessionconst db = scopedClient(tenant);                      // one schema, one storage prefixassertTenant(db, tenant);                             // refuses the sister company

Step 4 / 7 · Recall

Recall

ARIA pulls the last report, the content plan and earlier notes from this project, so the new report continues the old one instead of starting over.

trace
recall({ project: 'weekly-marketing' }) →  last_report: "w46", plan_rows: 18, open_actions: 3

Step 5 / 7 · Claude

Read the live numbers

The model calls read tools: content published this week, reach and engagement, sign-ups from campaigns. Numbers come from the database, the model only writes the words around them.

trace
→ query_metrics { range: "this_week", metrics: ["posts","reach","signups"] }← { posts: 11, reach: 48210, signups: 37, best: "REL-04" }

Step 6 / 7 · Tools

Draft, then wait

The report and three post ideas are written as drafts. The stable instructions are cached, which is why a report now costs about eight cents instead of thirty.

trace
→ report_save   { status: "draft" }→ content_plan  { add: 3, status: "proposed" }      // not published

Step 7 / 7 · Approval

A human approves

Anything that leaves the building, like an email, a post or a status change, goes to an approval queue. A person with the right role presses approve; the action and the approver are logged.

postgresql
insert into approvals (tenant, action, payload, requested_by)values ($1, 'publish_post', $2, $3);       -- waits-- on approve: run action, write audit_log (who, what, when)

04

Code

Two pieces that carry the most weight in this agent.

Every tool call passes the same gate: role, company, then approval for anything that writes.

aria/run_tool.jsjavascript
export async function runAriaTool(call, session) {  const tool = REGISTRY[call.name];  if (!tool || !tool.roles.includes(session.role)) return deny('not allowed for this role');   const input = tool.schema.parse(call.input);           // reject bad arguments  const db = scopedClient(session.tenant);              // company comes from login   if (tool.writes) {    const id = await queueApproval(db, { tool: call.name, input, by: session.user });    return { status: 'waiting_for_approval', id };  }  const result = await tool.run(db, input);  await audit(db, session, call.name, input);  return redact(result);                                // no keys, no personal data}

Part of the isolation suite that runs on every deploy: company A must not reach company B in any way.

aria/isolation.test.jsjavascript
for (const [me, other] of [[CAP, MS], [MS, CAP]]) {  const db = scopedClient(me);  await expectDenied(() => db.schema(other.schema).from('users').select('*'));  await expectDenied(() => db.storage.from(other.bucket('files')).list());  await expectDenied(() => runAriaTool(    { name: 'query_metrics', input: { tenant: other.id } }, sessionOf(me)));}
05

Data and guardrails

What it keeps

  • conversations · projectsthreads grouped per projectper company
  • reportsdaily, weekly and monthly work reportsarchive with approval status
  • approvalspending actions waiting for a personuntil approved or rejected
  • audit_logwho asked what, which tool ran, who approvedkept for review

What keeps it safe

  • Company from loginThe tenant is never read from the chat, so no prompt can switch companies.
  • Tools by roleA tool the role may not use is never offered to the model at all.
  • Writes waitEmails, posts and status changes need a person to approve.
  • No secrets in contextKeys and personal data are stripped from tool results before the model sees them.
