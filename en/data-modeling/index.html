Career Agent: application lifecycle

One request, step by step

A learner asks the Career Agent to tailor their CV to a job ad. The agent uses two Claude models: a small, fast one (Haiku) for conversation and a stronger one (Sonnet) for writing documents. When the small model tries to write the CV, the router stops that step and replays it on the stronger model. Chat stays cheap; documents stay good.

Hourly candles become features with no look-ahead (every input is shifted one bar). A trend filter plus an RSI pull-back decides direction; position size targets 40% annualised volatility; fees are charged on every change in position.

northstar/market_desk/backtest.pypython
import numpy as np, pandas as pd YEAR = 24 * 365sharpe = lambda r: r.mean() / r.std() * np.sqrt(YEAR) # 1 · candles → features (no look-ahead: every feature is shifted)px = candles["close"]f = pd.DataFrame(index=px.index)f["ret"]   = np.log(px).diff()f["ema_f"] = px.ewm(span=12, adjust=False).mean()f["ema_s"] = px.ewm(span=48, adjust=False).mean()delta      = px.diff()gain, loss = delta.clip(lower=0), -delta.clip(upper=0)rs         = gain.ewm(alpha=1/14).mean() / loss.ewm(alpha=1/14).mean()f["rsi"]   = 100 - 100 / (1 + rs)f["vol"]   = f["ret"].rolling(24 * 7).std() * np.sqrt(YEAR) # 2 · signal: trend filter + RSI pull-back, sized to a 40% vol targetlong   = (f["ema_f"] > f["ema_s"]) & (f["rsi"] < 65)weight = (0.40 / f["vol"]).clip(upper=1.0).where(long, 0.0).shift(1) # 3 · backtest, 10 bp fee on every change in positionfee    = 0.001 * weight.diff().abs().fillna(0)strat  = weight * f["ret"] - feeequity = np.exp(strat.cumsum())dd     = equity / equity.cummax() - 1hold   = np.exp(f["ret"].cumsum()) report = pd.DataFrame({    "strategy": [equity.iloc[-1] - 1, sharpe(strat), dd.min()],    "buy_hold": [hold.iloc[-1] - 1, sharpe(f["ret"]), (hold / hold.cummax() - 1).min()],}, index=["return", "sharpe", "max_drawdown"]).round(3)print(report)print(f"trades={int((weight.diff().abs() > 0.05).sum())}  exposure={(weight > 0).mean():.0%}")

Should I trust the market desk’s trend signal?

The market desk says when Bitcoin is in an uptrend (be in) and when it is not (stay out). Before any signal goes live, I replay it on two years of prices: follow the signal, pay a fee on every trade, and compare the result with buying once and simply holding. A signal earns its place if it cuts the big losses without giving up too much of the gains.

  1. Top chart: the price with a fast and a slow average. When the fast line crosses above the slow one, the signal says buy (▲); below it, sell (▼).
  2. Bottom chart: what 100 becomes if you follow the signal, against what it becomes if you just hold.

Nightly data checks

Small programs that run on their own and check that the data still makes sense: money, payments, privacy, links, interviews and backups. Each one stays silent when everything is fine and sends one email with the exact rows when it is not, so problems are fixed before a customer notices. Open a check to see what it reads, a real problem it caught, and its code. Then run them all, or break something first.

  1. 1On a schedulenightly, weekly, every 10 minutes or on every deploy
  2. 2Read the dataa read-only query over the live tables
  3. 3Compare with a ruleeach rule is something that must always be true
  4. 4Quiet or alertall good: nothing; a problem: one email with the exact rows
discount-healthDiscounts and orders agree

Catches: an order with a code whose price did not drop, a code past its quota, an expiry that is not 23:59

How it works
What it does

Reads every active voucher, referral and creator code plus the last 14 days of orders, and tests nine rules: valid percentage, no free orders, expiry at 23:59 local time, quota not exceeded, usage count equals real orders, no duplicate names, a code always lowers the price, promo and code never stacked, no quota slot held longer than 48 hours.

A real catch

Codes saved as midnight in UTC were expiring at 07:00 local time on their last day. The check flagged eleven of them; all now end at 23:59.

reconcile-paymentsPayments match the provider

Catches: an order paid at the provider but still pending here, so the buyer never got credits

How it works
What it does

Takes every order still marked pending and asks the payment provider for its real status. Paid orders are completed through the same code path as the live webhook, so credits and invoices arrive exactly once. Orders the provider never saw are closed after 48 hours.

What it does
